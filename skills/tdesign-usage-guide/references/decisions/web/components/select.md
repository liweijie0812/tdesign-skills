# Web Select 何时使用

本文描述 Web 场景下 `Select` 的设计选型。具体 props、事件、插槽、子组件和类型必须回到当前技术栈 API 确认。

## 何时使用

- 当需要在有限空间中展示大量选项，并从中选择一个或多个值时使用。
- 选项较多时，应提供搜索能力。
- 下拉面板出现时，应保证仍位于页面可视区域内。
- 操作收纳使用 `Dropdown`，不要用 `Select` 承担操作菜单。
- 选项是扁平列表，用户只需要选择一个或多个值时优先使用 `Select`。
- 选项用于表单筛选、状态、类型、负责人、标签等常见字段时适合使用 `Select`。

## 选型要点

- 先判断用户是在选择值，而不是执行命令；执行命令应使用 `Button`、`Dropdown` 或菜单类组件。
- 选项较少且需要全部可见时优先考虑 `Radio`；选项较多、空间有限或需要搜索时使用 `Select`。
- 多选场景要确认已选项展示、清除、溢出和搜索方式，避免选择结果不可读。
- 远程搜索、虚拟滚动、创建新选项等能力必须回到当前技术栈 API 确认，不从设计规则反推。

## 相关取舍

- 相似组件取舍见 `../similar-components.md`，优先按当前平台和当前技术栈确认。
- 常见相关组件：`Cascader`、`TreeSelect`、`Dropdown`。
- 选项是层级路径时使用 `Cascader`；需要紧凑选择树节点时使用 `TreeSelect`；需要浏览、展开、勾选或操作完整层级结构时使用 `Tree`。

## 反模式

- 不要把其他端或其他技术栈的 API、事件、插槽和样式写法直接套用到当前平台。
- 不要为了视觉接近而用自定义浮层重做 TDesign Select。
- 当前组件不能满足需求时，先查 `Cascader`、`TreeSelect`、`Transfer` 和降级策略，不要直接引入其他组件库或手写临时结构。
- 不要把无层级关系的普通枚举做成 `Cascader`，也不要把动作项放进 `Select` 让用户“选择一个操作”。
- 少量可见互斥选项优先考虑 `Radio`，不要为了统一样式强行下拉。
