# Web Dialog 何时使用

本文描述 Web 场景下 `Dialog` 的设计选型。具体 `visible`、`theme`、`mode`、`placement`、`width`、`confirmBtn`、`cancelBtn`、`confirmLoading`、关闭事件、插件调用和挂载能力必须回到当前技术栈 API 确认。

## 何时使用

- 当前任务必须被局部中断，用户需要先完成确认、告警、短表单或关键决策时使用。
- 内容较短，主要是确认、提示、少量字段编辑、结果反馈或必要信息补充。
- 操作有风险或不可逆，需要明确的确认按钮和结果导向文案。
- 需要用户聚焦在当前决策，不应继续浏览或操作页面其他区域。

## 与相似组件

- 轻量、低到中等风险的二次确认优先使用 `Popconfirm`。
- 需要更多空间并保留主页面上下文时使用 `Drawer`。
- 完全自定义浮层且标准组件无法满足时才考虑 `Popup`。
- 操作后的短反馈使用 `Message`，持续页面提示使用 `Alert`，不要默认弹窗。

## 内容与按钮

- 标题应说明决策对象，正文应说明原因、影响和后果。
- 确认按钮文案应表达操作结果，例如“删除项目”“提交审批”，不要只写“确定”。
- 危险操作应使用危险语义，并考虑二次确认、权限校验或撤销机制。
- 短表单可以放入 `Dialog`；复杂表单、长列表、多步骤配置应使用 `Drawer` 或页面。
- 默认底部按钮足够时不要过度自定义 footer；自定义按钮时必须自行处理确认、取消和关闭逻辑。

## 关闭与异步

- 异步确认时使用确认按钮加载状态，避免重复提交。
- 表单校验未通过时不要关闭弹窗，应在弹窗内展示字段错误。
- 点击蒙层、关闭按钮、ESC 关闭是否允许，要按任务风险决定。
- 高风险或未保存内容场景，应拦截关闭或二次确认，避免误操作。
- 关闭后是否销毁内容取决于表单状态保留需求，必须按当前栈 API 确认。

## 反模式

- 不要把大型复杂表单、宽表格或多步骤流程塞进 `Dialog`。
- 不要用 `Dialog` 承载普通成功提示，轻反馈优先 `Message`。
- 不要用 `Dialog` 替代页面导航或常驻配置面板。
- 不要把移动端弹窗规则、底部弹层和手势交互直接套到 Web。
