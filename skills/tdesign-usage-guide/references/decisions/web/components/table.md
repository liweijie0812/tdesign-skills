# Web Table 何时使用

本文描述 Web 场景下 `Table` 的设计选型。具体 `columns`、`data`、`rowKey`、`pagination`、`loading`、`empty`、固定列、虚拟滚动、展开、选择、编辑、拖拽和列配置能力必须回到当前技术栈 API 确认。

## 何时使用

- 当需要展示大量结构化行列数据，方便用户浏览、比较和获取批量信息时使用。
- 当数据需要排序、搜索、筛选、分页、选择、展开、编辑或自定义行操作时使用。
- 当用户需要横向对比字段、分析差异、归纳分类或批量处理记录时使用。
- 结构相似但横向字段对比不是重点时，优先使用 `List`；只读事实详情优先使用 `Descriptions`。

## 数据与列设计

- 每行必须有稳定唯一标识，按当前栈 API 设置 `rowKey`。
- 列应围绕核心任务设计，不要把所有后端字段原样铺出。
- 重要字段靠前，低频字段可收纳到展开行、详情页或列配置中。
- 数字、金额、时间、状态、操作等字段应使用一致的对齐和格式。
- 内容过长时使用省略、悬浮说明或展开详情，不要撑破表格布局。

## 交互能力

- 数据量较大时使用分页、服务端查询或虚拟滚动，不要一次性渲染全部数据。
- 需要保持上下文时可固定表头、固定列或吸底分页，但要确认滚动容器和吸附范围。
- 批量操作需要明确选择状态、操作影响范围和取消方式。
- 行内编辑适合少量字段和轻量修改；复杂编辑优先进入详情页、`Drawer` 或独立编辑页。
- 拖拽排序、列宽调整、列配置等高级能力只在用户确实需要个性化或高频处理时使用。

## 状态与反馈

- 加载中使用 `loading` 或页面级加载反馈，避免空白表格让用户误解为无数据。
- 无数据时使用 `Empty` 或表格空状态，并提供创建、重置筛选或重试动作。
- 查询失败、权限不足或部分失败应在表格上方或上下文内给出明确反馈。
- 单元格内容需要解释时可搭配 `Tooltip`，关键业务信息不应只放在悬浮层中。

## 操作列

- 高频操作直接展示，低频操作收纳到 `Dropdown`。
- 危险操作应搭配 `Popconfirm` 或 `Dialog`，并使用结果导向文案。
- 操作列不要堆叠过多按钮，优先控制在 2-3 个可见操作。
- 行操作、批量操作和页面主操作应保持层级清晰，不要互相抢焦点。

## 反模式

- 不要用 `Table` 展示少量详情字段，详情页优先 `Descriptions`。
- 不要把复杂宽表直接搬到移动端。
- 不要在表格里塞完整复杂表单，复杂编辑应拆到 `Drawer`、`Dialog` 或页面。
- 不要为了视觉整齐牺牲关键字段可读性和排序筛选效率。
