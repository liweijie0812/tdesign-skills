# TDesign 降级策略

优先使用 TDesign。只有确认 TDesign 当前栈没有对应组件、API 不满足需求、项目已有强约束，或目标能力属于业务封装时，才降级。

## 降级顺序

1. 优先查当前项目已有的 TDesign 封装组件。
2. 使用 TDesign 基础组件组合实现，例如 `Popup`、`Card`、`Space`、`Button`、`Form`。
3. 使用原生 HTML 与最小 CSS 补足缺失语义或布局。
4. 使用项目已安装并约定使用的其他组件库。
5. 新建业务组件，并明确它不是 TDesign 官方组件。

## 回答口径

- 明确说明为什么 TDesign 组件不足以覆盖需求。
- 说明降级方案是否依赖项目封装、第三方库或原生实现。
- 保留 TDesign 视觉和交互一致性，优先复用设计变量、间距、按钮和反馈组件。
- 不把降级方案包装成 TDesign 官方能力。

## 触发条件

- `meta/stack-matrix.json` 显示当前栈不存在目标组件。
- 当前栈存在同名组件，但缺少完成任务必须依赖的核心能力。
- 需求属于图表、富文本、拖拽编排、虚拟画布等明显超出 TDesign 组件边界的场景。
- 项目已经有稳定业务封装，替换成原生 TDesign 反而会破坏一致性。

## 降级前检查

- 是否误判了平台，导致把 Web 缺失能力套到了 Mobile，或反过来。
- 是否已有相近组件组合可以覆盖，尤其是 `Popup`、`Dialog`、`Drawer`、`Form`、`List`、`Cell` 这类基础能力。
- 是否只是缺少某个 props 或交互细节，而不是整个组件不存在。
- 是否需要先向用户澄清真实目标，再决定是否降级。

## 输出模板

- 先说明结论：当前栈是否有官方组件，是否需要降级。
- 再说明原因：缺的是组件本身、核心能力，还是项目约束。
- 最后给方案：优先写“TDesign 组合方案 / 项目现有封装 / 原生补足”三选一中的实际路径。

## 常见场景

- 复杂可视化图表：使用项目图表库，但容器、筛选、空状态、加载可用 TDesign。
- 富文本编辑器：使用项目编辑器方案，外层表单校验和反馈可用 TDesign。
- JSON Schema 表单：使用项目 schema 渲染器，底层字段组件可映射到 TDesign。
- 高度定制浮层：优先检查 `Dialog`、`Drawer`、`Tooltip`、`Popup` 是否足够，再补充自定义。
